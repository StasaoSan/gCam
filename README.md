# gCam — доступ к камерам 360° Geely G636

> ## Главное: откуда на самом деле брать видеопоток
>
> `Camera2` здесь использовать нельзя: пустой `cameraIdList` (`Available IDs: []`) является
> нормальным поведением этой прошивки. Камеры 360° подключены к отдельному AVM-контроллеру и
> обслуживаются сервисом
> `vendor.qti.automotive.qcarcam@1.0::IQcarCamera/default`, а не Android Camera HAL.
>
> Рабочая и проверенная на машине цепочка:
>
> ```text
> libais_hidl_client.so
>   → qcarcam_initialize()
>   → qcarcam_open(inputId)
>   → qcarcam_s_buffers(3 × ION DMA buffer, 1280×800 UYVY, stride 2560 bytes)
>   → qcarcam_start()
>   → qcarcam_get_frame()
>   → отобразить/обработать buffer[frame.idx]
>   → qcarcam_release_frame(frame.idx)
>   → qcarcam_stop() → qcarcam_close() → qcarcam_uninitialize()
> ```
>
> Начиная с v4.1 root для приложения не требуется: управляющий `/dev/ion` открывается как
> `O_RDONLY`, как в штатном Android `libion`. Возвращённые DMA-buffer fd остаются read/write.
> Поэтому достаточно штатного режима прошивки `0664 system:system`, а `mediacodec` не теряет ION.
>
> На G636 подтверждена точная раскладка: `0 — левая`, `1 — правая`, `2 — перед`,
> `3 — зад`. Технический вход `12` показывает то же направление, что `2`; вход `14`
> открывается, но обычно не отдаёт кадры вне активного режима заднего хода/RVC. В UI оставлены
> только четыре физические камеры. Формат — `UYVY 8-bit` (`0x07080102`), размер — `1280×800`, частота —
> `25 fps` (`14`: объявлено `30 fps`). Критически важно: поле `stride` в QCarCam ABI задаётся
> в **байтах**, поэтому для UYVY здесь это `1280 × 2 = 2560`, а не `1280`. Именно неверный
> stride давал `ais_start error 14`. Первый кадр приходит примерно через `240–252 ms`.
>
> Эталонная проверка без приложения:
>
> ```bash
> adb push tools/qcarcam_config_probe.xml /data/local/tmp/qcarcam_config_probe.xml
> adb shell su 0 /system/bin/qcarcam_hidl_test \
>   -config=/data/local/tmp/qcarcam_config_probe.xml \
>   -noDisplay -nonInteractive -nomenu -seconds=1
> ```
>
> Если в выводе есть `Success - First Frame`, весь путь AVM → HIDL → QCarCam работает.
> Готовый XML находится в [`tools/qcarcam_config_probe.xml`](tools/qcarcam_config_probe.xml).

## Что теперь делает приложение

Приложение содержит экран камер, регистратор и список записей и использует нативный
QCarCam-клиент. Диагностика,
монитор, запуск штатного AVM-окна, Camera2/Camera1/EVS fallback и экспорт логов удалены. Поток
запускается автоматически; снизу выбираются `Левая / Правая / Перед / Зад`.

Путь предпросмотра рассчитан на слабый CPU. На исследованной G636 фактически работает
вторая ветка:

```text
QCarCam → 3 cached ION DMA-BUF → CPU cache sync → PBO → GLES3 UYVY shader → TextureView
```

- нет RAW-файлов и дискового I/O;
- нет `Bitmap`, JPEG/PNG и объектов на каждый кадр;
- JNI не копирует кадр в Kotlin/Java;
- кадр не передаётся в Java/Kotlin, но при PBO fallback одна нативная копия на кадр остаётся;
- преобразование UYVY → RGB выполняет GPU;
- асинхронный GPU fence используется только на совместимом zero-copy пути;
- если DMA-BUF import недоступен, автоматически включается совместимый PBO fallback.

QCarCam на этой прошивке принимает буферы только из штатного non-secure ION heap
`0x02000000`. В старых версиях gCam `/dev/ion` ошибочно открывался как `O_RDWR`, из-за чего после
каждой перезагрузки требовался скрипт:

```bash
tools/prepare_ion_access.sh com.stasao.gcam.dev   # debug APK
# либо: tools/prepare_ion_access.sh com.stasao.gcam
```

В v4.1 скрипт больше не нужен. Он сохранён только для диагностики старых сборок. Менять
группу устройства на UID приложения нельзя: тогда процесс `mediacodec` теряет ION, Qualcomm
Codec2 падает при `createBlockPool`, а приложение получает `IllegalStateException`. SELinux
остаётся границей доступа; для исследованной прошивки дополнительных изменений не требуется.

Начиная с v4.3 запись, а теперь и preview/HUD, сначала пробуют zero-copy путь: каждый из трёх постоянных ION DMA-BUF
однократно импортируется через `EGL_EXT_image_dma_buf_import` как `640×800 ABGR8888`, где один
RGBA-тексель содержит пару `U/Y0/V/Y1`. Существующий шейдер получает те же четыре компонента,
но `memcpy`, PBO и `glTexSubImage2D` для каждого записываемого кадра исчезают. GPU fence удерживает
QCarCam-буфер до окончания чтения текстуры и только затем вызывает `qcarcam_release_frame()`.
Если расширения или хотя бы один EGLImage недоступны, камера автоматически возвращается на
проверенный PBO-путь.

На проверенной машине EGL-драйвер **не объявляет** `EGL_EXT_image_dma_buf_import`:
импорт UYVY и ABGR8888 заканчивается `EGL_BAD_PARAMETER (0x300c)`. Поэтому надпись
`PBO fallback` здесь ожидаема и сама по себе не означает ошибку. Для этой ветки gCam
по умолчанию выделяет кэшируемые ION-буферы и синхронизирует доступ CPU через
`DMA_BUF_IOCTL_SYNC`. Если выделение или синхронизация при запуске не поддерживаются,
приложение возвращается к прежним некэшируемым буферам. Для диагностики старый режим
можно принудительно включить системным свойством `debug.gcam.ion_cached=0` до запуска потока.

При первом создании EGL-контекста в logcat печатается диагностический probe: полные EGL/GL
extensions, адреса `eglCreateImageKHR`/`glEGLImageTargetTexture2DOES`, а также результаты
пробного импорта настоящего `DRM_FORMAT_UYVY` и рабочего packed-импорта `ABGR8888` с точным
`eglGetError`. Это позволяет отличить отсутствие расширения от неподдерживаемого pixel format.

## Важное ограничение доступа

`libais_hidl_client.so` — закрытая системная библиотека. Обычное приложение не может загрузить
её напрямую из `/system` из-за linker namespace, поэтому в APK входят device-matched клиент,
QCarCam HIDL-интерфейс и замкнутый набор их platform-зависимостей из исследованной прошивки
G636 (`libais_log`, `libmmosal`, HIDL/Binder/base/utils и другие зависимости).

Эти файлы нельзя считать переносимыми на другую модель или версию прошивки: после обновления
головного устройства их нужно заново извлечь и проверить ABI. SELinux/HIDL ACL всё равно должны
разрешать клиенту соединение; на исследованной машине SELinux был `Permissive`.

Живой тест 4 октября 2026 года подтвердил весь путь `initialize → open → setBuffers → start →
getFrame → releaseFrame` для inputs `0`, `1`, `2`, `3`. Все четыре изображения выведены на экран
с частотой 24–26 fps; последовательное переключение, закрытие и повторный запуск прошли без
падения. Штатный `qcarcam_hidl_test` независимо подтвердил первый кадр input 0 за 252 ms.

## Видеорегистратор (v4.3)

В приложение добавлен фоновый многокамерный регистратор. Он не передаёт кадры в Kotlin и не
кодирует видео на CPU:

```text
QCarCam ION/UYVY → EGLImage (если доступен) либо cached ION + PBO → GLES3 UYVY→RGB → MediaCodec Surface → аппаратный H.264 → MediaMuxer MP4
```

Для каждого физического input теперь создаётся не более одного QCarCam-захвата и одной загрузки
кадра в GPU. Оттуда кадр рисуется отдельно в Surface кодировщика и в запрошенные Surface HUD;
у каждого выхода собственные кроп и форма. Кодек не декодирует изображение: он принимает
нарисованный GLES-кадр и аппаратно кодирует H.264. Во время многокамерной записи обычный preview
по-прежнему закрывается до старта, чтобы не конкурировать за Surface регистратора.

Захват QCarCam и аппаратный MediaCodec работают в отдельных процессах (`:qcarcam` и
`:recorder`). Между ними передаётся только аппаратный `Surface`, без копирования кадров через
Java/Kotlin. Это не даёт закрытым QCarCam platform-библиотекам вмешиваться в Binder/Codec2
регистратора.

Настройки по умолчанию:

- камеры `2` (перед) и `3` (зад);
- H.264, `960×600`, `20 fps`, `3 Мбит/с` на камеру;
- MP4-сегменты по 2 минуты;
- циклический архив до 40 ГБ;
- неприкосновенный резерв свободного места 2 ГБ.

В интерфейсе можно независимо выбрать любые inputs `0–3`, разрешение
`640×400 / 960×600 / 1280×800`, частоту `15 / 20 / 25 fps`, битрейт `2 / 3 / 4 / 6 Мбит/с`,
сегменты `1/2/3/5` минут и лимит архива, рассчитанный из реально доступной памяти. Частота
ограничивается сразу после `qcarcam_get_frame()`: лишний кадр немедленно возвращается через
`qcarcam_release_frame()` до 2-МБ копирования, загрузки в GLES и передачи кодировщику.

MediaCodec получает выбранную частоту как `KEY_FRAME_RATE` и `KEY_OPERATING_RATE`, работает в
CBR с высоким приоритетом, без B-frames и с ключевым кадром раз в две секунды. Запись работает
через foreground service и продолжается после закрытия экрана приложения. Неизменяемый резерв
свободного места — 2 ГБ. Максимум архива рассчитывается как свободное место плюс объём
существующих записей gCam минус резерв. В интерфейсе показываются общий объём, занятое и свободное место,
размер архива gCam и примерная длительность записи.

Три независимых переключателя добавляют в сам MP4 дату/время, GPS-координаты и скорость,
рассчитанную по GPS. Текст обновляется примерно раз в секунду и рисуется маленькой областью
GLES перед аппаратным H.264-кодированием; видеокадры для этого не читаются обратно на CPU.
Для GPS и скорости требуется разрешение Android на точное местоположение. Если свежего
определения нет, метка показывает `GPS --` и `-- KM/H`, а не старые значения. При автозапуске
в фоне Android может не разрешить доступ к геолокации; запись и метка времени продолжают
работать. Работа меток на G636 ещё требует проверки на устройстве.

Готовые файлы видны обычному файловому менеджеру в `Movies/gCam/camera_N`. Записи старых
версий автоматически переносятся туда из приватного каталога. Во вкладке «Записи» есть встроенный
видеоплеер, защита от циклической очистки и удаление. При переполнении сначала удаляются самые
старые незащищённые сегменты. Масштаб всего интерфейса регулируется в диапазоне 130–180% и
сохраняется между запусками.

Плеер показывает соседние сегменты одной камеры как одну запись с общей длительностью,
постоянными кнопками воспроизведения/паузы и перемоткой по всей последовательности. При
переходе через границу он открывает следующий MP4 без копирования или перекодирования.
Новые сегменты помечаются ID сеанса, старые группируются по времени с допуском до 5 секунд;
разрыв оставляет отдельные записи. Исходные MP4 доступны через «Показать файлы» для защиты
и удаления по отдельности. Физической склейки файлов пока нет.

Если питание пропадёт в процессе записи, может потеряться только открытый короткий сегмент;
завершённые MP4 не затрагиваются. Остаточный `.tmp` удаляется при следующем старте регистратора.

На SA8155 проверена одновременная запись всех четырёх inputs: четыре аппаратных H.264-кодека
создали ION block pools, все камеры вышли в активный поток, а четыре MP4 корректно завершились
примерно по 22 МБ и содержали по 1240–1263 кадра. Длительную температурную проверку ещё нужно
провести отдельно.

На G636 11 октября 2026 года кэшируемый ION уменьшил среднее время `memcpy` с
примерно 8–9 мс до 0,35–0,41 мс на кадр. Короткий прогон `4 × 960×600 × 25 fps`
дал примерно 24,6–25,6 FPS в живом счётчике, без QCarCam timeout. В одинаковых
коротких запусках Android `top` показывал для процесса `:qcarcam` примерно
93–130% CPU с некэшируемыми буферами против 23–28% с кэшируемыми (100% — одно
ядро); процесс `:recorder` оставался примерно на 31–40%. Четыре
завершённых MP4 из более длинного прогона читаются `ffprobe`; в одном сегменте
каждой камеры фактически записано примерно 23–23,5 FPS. Это **не** zero-copy,
и эти короткие CPU-замеры не заменяют длительную проверку температуры и FPS.

### Проверка производительности zero-copy

Нативная часть считает по каждой камере среднее и максимальное время `getFrame`, `memcpy`,
загрузки PBO (включая cache sync), отправки команд GPU, `eglSwapBuffers`, удержания ION-буфера и максимальную паузу между
записанными кадрами. Каждые пять секунд сервис пишет одну строку `GCAM_PERF`; поле
`mode=zero-copy` подтверждает, что PBO fallback не использовался. `gpuSubmit` — именно время
отправки команд с CPU, а не аппаратное время исполнения шейдера.

Обычная проверка выполняется прямо в приложении. На каждом окне preview и возле каждой
записываемой камеры показываются:

- `ZERO-COPY` зелёным, если ION DMA-BUF успешно импортирован в EGLImage;
- `PBO fallback` оранжевым, если драйвер отклонил прямой импорт;
- текущий FPS и максимальная замеченная пауза между кадрами.

Обычно достаточно открыть приложение или начать запись на 10–20 секунд. На этой прошивке
ожидается `PBO fallback`; успех проверяется по FPS, отсутствию timeout и готовым MP4.

### Диагностика длительной записи

Во вкладке записи есть кнопка «Поделиться диагностикой записи». Журнал сохраняется на устройстве
между запусками приложения и после перезагрузки G636; последние два файла занимают не более
примерно 2 МБ. Каждые 15 секунд во время записи фиксируются FPS, паузы и timeout каждой камеры,
число кадров и байт на выходе H.264, возраст последнего кадра кодера, состояние потока записи,
число завершённых MP4, CPU отдельно для `:recorder` и `:qcarcam`, память процессов и свободное место.
Также записываются запуск, остановка, смена сегментов и ошибки. Проценты CPU считаются относительно
одного ядра, поэтому на многоядерном процессоре могут быть больше 100%.
В журнал также входят PSS и графическая память обоих процессов, доступная ОЗУ системы и события
`trim_memory`. При повторном падении доступной ОЗУ ниже 512 МБ регистратор завершает запись,
чтобы не довести G636 до полной остановки. Для записи PBO-буферы переиспользуются только после
GPU fence: драйвер больше не должен выделять новые 2-МБ хранилища при отставании кодера.

Выбранные камеры передаются сервису записи напрямую, а не только через настройки другого
процесса. Перед стартом gCam дожидается закрытия четырёх превью. Это устраняет гонку, при
которой после выбора четырёх камер запускались только две.

Общий захват для записи и HUD одного input реализован в нативном конвейере, но ещё не проверен
на машине. Если боковая камера включена в ANHUD, её QCarCam-захват может оставаться «тёплым»:
пока окно скрыто, кадры сразу освобождаются без загрузки в GPU. При поворотнике ANHUD подключает
Surface к уже запущенной камере. Метрика `firstFrameMs` теперь отсчитывается от запроса показа,
чтобы измерять задержку именно поворотника, а не время работы приложения.

Если после длительной записи устройство тормозит, остановите запись, при необходимости перезагрузите
G636, затем откройте gCam и отправьте диагностический файл этой кнопкой. Не очищайте данные приложения
перед экспортом: это удалит журнал. Во время проверки приложение не делает скриншотов и не сохраняет
кадры в диагностику.

Для необязательной автоматизированной проверки через ADB остаётся короткий сценарий:

```bash
tools/run_zero_copy_acceptance.sh \
  -s 192.168.119.246:5555 \
  --duration 20
```

Он запускает запись `4 × 960×600 × 20 fps`, собирает `GCAM_PERF` и CPU процессов
`:qcarcam`/`:recorder`, сохраняет список новых MP4 и скачивает их в
`build/zero-copy-acceptance-*`. Если на Mac установлен `ffprobe`, параметры каждого файла
проверяются автоматически. Параметры `--duration 600 --cycles 10` оставлены только для
необязательного стресс-теста перед длительной эксплуатацией — они не нужны для обычной проверки
работоспособности zero-copy.

## Боковые камеры в ANHUD (v4.4)

gCam экспортирует защищённый Binder/AIDL-сервис для ANHUD. ANHUD передаёт в него аппаратный
`Surface`, а gCam выводит туда input `0` (левый поворотник) или `1` (правый) напрямую через
QCarCam и GLES:

```text
CarProxy turn signal → ANHUD → Surface по Binder → gCam :qcarcam
  → QCarCam ION/UYVY → GLES → TextureView ANHUD → единый слой 800×480 → QNX HUD
```

Кадры проекции не сериализуются через AIDL и не превращаются в `Bitmap`/JPEG. Отдельный мост
приборки QNX пока читает уменьшенную копию кадра из TextureView в CPU; там оставлен только
последний ожидающий кадр каждой стороны и переиспользуются буферы для чтения.
Доступ к сервису проверяется по фактическому UID каждого Binder-вызова. Только пакет
`com.g992.anhud` может использовать HUD-команды; управление записью остаётся внутри gCam.
Если ANHUD подписан тем же ключом, что gCam (например, две debug-сборки с одного ноутбука),
доступ автоматический. При другой подписи откройте в gCam раздел «Доступ ANHUD к камерам» и
подтвердите установленный ANHUD. gCam сохранит отпечаток его текущего сертификата; после смены
подписи понадобится повторное подтверждение. Секрет внутри открытого ANHUD не требуется.

HUD-поток ограничен 15 fps и показывается только после первого полученного кадра. При аварийке
камера не выбирается, потому что направление неоднозначно. ANHUD остаётся единственным владельцем
кастомного HUD-слота: видео занимает только центральный прямоугольник, штатная приборка остаётся
видна снаружи, а элементы ANHUD рисуются поверх камеры.

В ANHUD боковые камеры имеют отдельный переключатель, независимый от проекции иконок
поворотников. Нажатие на карточку камер открывает редактор: окно можно перетащить, независимо
изменить ширину и высоту и выбрать прямоугольную, скруглённую или овальную форму. Геометрия и
форма входят в пресеты/экспорт настроек ANHUD.

Для общего захвата и предварительного прогрева нужно обновить оба приложения: сначала gCam,
затем ANHUD. При разных подписях подтвердите ANHUD в настройках gCam. Второй QCarCam handle для
записи и проекции одного input больше не открывается. Реальное поведение и снижение задержки
необходимо проверить на G636 перед длительной эксплуатацией.

### Автозапуск и точка состояния

В нижней части вкладки «Камеры и запись» находятся независимые настройки:

- автозапуск gCam поднимает только фоновый QCarCam-мост для ANHUD, без открытия главного окна
  и четырёх preview;
- автозапуск записи дополнительно запускает регистратор с последними сохранёнными камерами и
  параметрами;
- точка состояния показывает фактическое состояние обмена кадрами: красный — нет связи с ANHUD
  или кадров, оранжевый — связь установлена и HUD получил видео, зелёный — одновременно идёт
  успешная запись.

Основной запуск выполняется через `BOOT_COMPLETED`, `QUICKBOOT_POWERON` и `USER_PRESENT`.
Некоторые автомобильные прошивки подавляют обычные boot broadcast, поэтому предусмотрена
резервная служба специальных возможностей. Она не читает содержимое окон и используется только
как системный сигнал после загрузки. Включить её можно кнопкой «Открыть специальные возможности»
в самом gCam. Для точки Android отдельно попросит разрешение «поверх других приложений»; точку
можно перетащить, а короткое нажатие открывает gCam.

## Сборка

```bash
export JAVA_HOME="/opt/homebrew/opt/openjdk@17/libexec/openjdk.jdk/Contents/Home"
./gradlew assembleDebug
```

Проект собирает только `arm64-v8a`, что соответствует G636. Нужны Android SDK и NDK
`28.2.13676358`.

### Выпуск и обновление через GitHub

Проверка кода запускается на `main`, pull request и при ручном запуске. Тег `v*` после успешных
тестов собирает подписанный release APK и публикует GitHub Release с соответствующим разделом
[`CHANGELOG.md`](CHANGELOG.md). Для тега `v4.93` файл будет называться `gCam_[v4.93].apk`.
Временные артефакты Actions хранятся 1 день; файлы опубликованного Release остаются доступны.

Репозиторий `StasaoSan/gCam` и его Releases должны быть публичными: приложение проверяет
обновления по этому адресу. Отдельный репозиторий и токен для публикации не требуются — workflow
использует встроенный `GITHUB_TOKEN` с доступом только к текущему репозиторию.

Для первого выпуска один раз подготовьте постоянный ключ подписи. В GitHub-репозитории откройте
**Settings → Secrets and variables → Actions** и добавьте четыре секрета:

- `SIGNING_KEYSTORE_BASE64` — содержимое keystore, закодированное Base64;
- `SIGNING_STORE_PASSWORD` — пароль хранилища;
- `SIGNING_KEY_ALIAS` — имя ключа;
- `SIGNING_KEY_PASSWORD` — пароль ключа.

Пример создания нового ключа на Mac (сохраните `.jks` и пароли отдельно от репозитория):

```bash
keytool -genkeypair -v -keystore gcam-release.jks -alias gcam \
  -keyalg RSA -keysize 3072 -validity 10000
base64 -i gcam-release.jks | tr -d '\n'
```

Если у установленного `com.stasao.gcam` уже есть постоянный ключ, используйте именно его:
Android принимает обновление только с прежней подписью. Подписи gCam и ANHUD могут различаться:
при первом подключении ANHUD с другим сертификатом подтвердите его в gCam. Сборка `com.stasao.gcam.dev`
является отдельным приложением; первый подписанный release APK устанавливается вручную один раз.

Перед выпуском увеличьте `versionCode`, установите соответствующий тегу `versionName` в
`app/build.gradle.kts` и добавьте раздел в changelog. Затем отправьте коммит в основную ветку и
выпустите **новый** тег на этом коммите. Тег `v4.92` указывает на коммит с версией APK `4.91`,
поэтому его сборка не прошла проверку; переписывать опубликованный тег не нужно. Следующий выпуск — `v4.93`:

```bash
git add app/build.gradle.kts CHANGELOG.md README.md
git commit -m "[v4.93] align release version and changelog"
git push origin main
git tag v4.93
git push origin v4.93
```

Во вкладке «Обновление» gCam проверяет последний Release `StasaoSan/gCam`, показывает заметки,
скачивает APK и проверяет его размер, SHA-256, пакет, версию и подпись. Затем открывает системный
установщик. При первом обновлении Android попросит разрешить установку из gCam. Установку нужно
подтвердить вручную; во время записи сначала завершите текущие MP4. Для проверки релизов из
самого приложения репозиторий с APK должен быть публичным.

Готовый debug APK после сборки: `app/build/outputs/apk/debug/app-debug.apk`. Установка на
конкретную машину, когда ADB видит несколько устройств:

```bash
adb -s 192.168.119.246:5555 install -r app/build/outputs/apk/debug/app-debug.apk
```

После первой установки приложение само запрашивает доступ к видео/мультимедиа и уведомлениям.
Запускать `prepare_ion_access.sh`, менять владельца `/dev/ion` или выдавать root-права больше не
нужно. Android не разрешает сохранять видео MediaStore непосредственно в корень `Download`,
поэтому публичный архив находится в разрешённой системной папке `Movies/gCam`.
